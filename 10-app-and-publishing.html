12  The app, and publishing

Two stages are left: an explorer so that people can interrogate the estimates themselves, and the command that puts this book on the web.

12.1 Anatomy of a Shiny app

Every Shiny app is three objects and one idea.

Piece What it is In this app
ui a nested list of HTML widgets fluidPage(sidebarLayout(...))
server a function of input, output, session computes the estimates, draws the plot
shinyApp(ui, server) wires them together and serves them the last line of the file

The idea is reactivity. You never write “when the user clicks, recompute.” You declare what each output is, in terms of inputs, and Shiny works out what to re-run when something changes.

input$by

the control

est()

reactive

output$plot

render

Three kinds of object in that chain, and the distinction is the whole framework:

  • input$x — read-only, set by the browser. Touching input$state anywhere makes that code depend on it.
  • reactive({ ... }) — a computation that caches and re-runs only when something it read has changed. est() is called by both the plot and the table, and runs once.
  • render*({ ... }) — an output. It re-runs when a dependency changes and writes into output$plot.

The two mistakes agents make here Asking for a reactive’s value outside a reactive context (est() at the top level — “operation not allowed without an active reactive context”), and recomputing the same summary separately in each render* block instead of sharing one reactive(). The second one is not an error; it is just the app doing the work twice.

12.1.1 This app, line by line

#> library(shiny)
#> library(tidyverse)
#> source(here::here("R/functions.R"))
#> 
#> wss <- read_rds(here::here("data/wss_clean.rds"))
#> 
#> ui <- fluidPage(
#>   titlePanel("Western States Survey: Trump vote, 2020 vs 2024"),
#>   sidebarLayout(
#>     sidebarPanel(
#>       checkboxGroupInput("state", "State", sort(unique(wss$state)), sort(unique(wss$state))),
#>       selectInput("by", "Compare by", c("latino", "race4", "auth_group", "age_group", "party3")),
#>       checkboxInput("wt", "Use survey weights", TRUE)
#>     ),
#>     mainPanel(plotOutput("plot"), tableOutput("tab"))
#>   )
#> )
#> 
#> server <- function(input, output, session) {
#>   est <- reactive({
#>     wss |>
#>       filter(state %in% input$state) |>
#>       trump_share(input$by, weighted = input$wt)
#>   })
#>   output$plot <- renderPlot(
#>     ggplot(est(), aes(year, trump, colour = .data[[input$by]], group = .data[[input$by]])) +
#>       geom_point(size = 3) + geom_line() +
#>       scale_y_continuous(labels = scales::percent, limits = c(0, 1)) +
#>       labs(x = NULL, y = "Two-party Trump share", colour = NULL) +
#>       theme_minimal(base_size = 15)
#>   )
#>   output$tab <- renderTable(est())
#> }
#> 
#> shinyApp(ui, server)
Rscript -e 'shiny::runApp("app")'

Read it top to bottom:

  1. Load once, outside server. Code above ui runs a single time when the app starts, not per user and not per click. The data read belongs there.
  2. source("R/functions.R"). The app calls trump_share() — the same function the analysis script calls. The app holds no analysis logic of its own, so it cannot drift away from the paper.
  3. The UI names the inputs. inputId = "by" in the UI is input$by in the server. That string is the entire contract between the two halves.
  4. .data[[input$by]] — the tidy-evaluation form for a column chosen at runtime. An agent will often write get(input$by) or paste strings together; both work until they don’t.
  5. A weights toggle. Making “weighted or not” visible in the interface is honest, and it shows the audience how much the weighting is doing.
  6. n_obs and n_miss in the table. Every point in the plot has a sample size behind it, and some of them are small.

12.1.2 Why it is testable

server is an ordinary R function, so it can be run without a browser — shiny::testServer() sets inputs and reads the reactives back. That is what the app’s integration tests do. Two habits make an app testable at all: keep the computation in a named function outside the app, and keep the server body thin enough to read.

What this app would need before anyone else used it Cell-size suppression, for one — a filtered panel can easily land on fewer than 30 respondents, and a point estimate drawn from them invites exactly the over-reading this project is about. Intervals, too; the plot shows points with no uncertainty at all.

12.2 Publishing

The site, the book, and the slides are one Quarto project:

quarto render                 # build everything into _site/
quarto preview                # live reload while writing
quarto publish gh-pages       # render, then push to the gh-pages branch

quarto publish gh-pages commits the rendered output to a gh-pages branch and leaves your source branch alone. GitHub Pages serves it at crweber9874.github.io/UNM_Workshop.

12.2.1 Freeze, and why it is committed

execute:
  freeze: auto

Chapters that run R store their results in _freeze/. A rebuild re-runs only what changed, which keeps the render fast and means the book can be rebuilt on a machine without the data. Delete _freeze/ and render again when you want to prove the whole thing still reproduces.

12.2.2 What is deliberately not committed

Not committed Why
data/wss_clean.rds regenerate it: Rscript R/01_recode.R
output/ figures and tables are rebuilt by R/02_analysis.R
_site/ rendered output; gh-pages holds the published copy
.Renviron, .env secrets never belong in a repository
raw .dta files not ours to distribute

The principle: commit the instructions for producing a thing, not the thing — unless the thing is expensive to produce and cheap to store, which is the argument for _freeze/.

12.3 The whole pipeline, one command at a time

Rscript R/01_recode.R                              # csv  -> data/wss_clean.rds
Rscript R/02_analysis.R                            # models, figures -> output/
Rscript -e 'testthat::test_dir("tests/testthat")'  # checks pass?
Rscript -e 'shiny::runApp("app")'                  # explore
quarto render                                      # book + slides -> _site/
quarto publish gh-pages                            # publish

Six commands, one direction, no step that depends on something a person remembered to do by hand. That is the standard an agent has to be held to as well — and how you hold it there is the last chapter.
