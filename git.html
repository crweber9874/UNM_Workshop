2. Git workflow

The model

Working directory → Staging area → Local repo → Remote (GitHub)
     (edit)            (add)        (commit)        (push)
                                         ←  (pull)  ←

Changes move left to right, one deliberate step at a time, and come back with git pull. The staging area exists so you can commit some of your changes — the finished recode, not the half-written one beside it.

Fork vs. clone

Fork makes a copy of someone else’s repository under your account, on the GitHub website. Use it when you want to contribute to a project you cannot write to. Fork + clone + pull request is how open-source collaboration works.

Clone makes a copy on your computer:

git clone https://github.com/crweber9874/UNM_Workshop.git
cd UNM_Workshop

Your edits stay local until you push, and you can only push to repositories you have access to.

Today Everyone is a collaborator on one repository, so you clone and work on branches. If you would rather keep your work separate, fork first and open pull requests from your fork — the workflow below is otherwise identical.

The everyday loop

git pull                     # ALWAYS first: get everyone else's work
git status                   # what changed?
git add R/01_recode.R        # stage specific files (avoid `git add .` blindly)
git commit -m "Recode age into generations"
git push

A commit is a snapshot of your changes with a unique ID and a message. The message is for the version of you who, in four months, needs to know why age_group has four categories. Write it for that person.

Working together in one repository

git pull
git switch -c weber-recode-generation     # your own branch
# ...edit, add, commit...
git push -u origin weber-recode-generation
gh pr create --fill                       # open a pull request

Someone reviews the pull request on GitHub and merges it. Then everyone returns to a common base:

git switch main && git pull

When to use what

Action When Command
Fork Contributing without write access on github.com
Clone Getting a repo onto your machine git clone <url>
Pull Before you start working git pull
Branch Any change you are not sure of git switch -c name-topic
Add Choosing what goes in the commit git add R/01_recode.R
Commit Saving a coherent step locally git commit -m "message"
Push Publishing your branch git push -u origin name-topic
Pull request Asking for review and a merge gh pr create --fill

Rules of the road Pull before you start, push when you stop · one person per file where possible (recode / analysis / app) · small commits with clear messages · never commit data you were not given, passwords, or .Renviron.

Merge conflicts

<<<<<<< HEAD
your version
=======
their version
>>>>>>> main

Keep what is right, delete the markers, then git add and git commit. You can ask the agent — “resolve the merge conflict in R/01_recode.R, keeping both recodes” — and then read its diff.

Undo

Situation Command
See what you changed git diff
Discard edits to a file git restore file.R
Unstage git restore --staged file.R
Fix the last commit message git commit --amend (before pushing)
Undo a pushed commit git revert <hash>
Look at the history git log --oneline -10
